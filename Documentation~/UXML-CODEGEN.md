# Typed queries and UXML codegen

Two features that turn "the UXML and the code drifted apart" from a silent
`NullReferenceException` into a loud, named failure:

1. **`Require<T>`** — `Q<T>` that throws instead of returning null.
2. **UXML → typed view codegen** — a generated partial class per UXML file, with one typed
   property per named element and an `AssignQueries` that resolves them all through
   `Require<T>`, kept honest by auto-regen in the Editor and a byte-exact drift check in CI.

## `Require<T>`

`Runtime/Utilities/VisualElementQueryExtensions.cs`, namespace `Cuvara.UIToolkit.Utilities`:

```csharp
Label title = root.Require<Label>("popup-title");
```

Found: returns the element, never null. Missing — or present under that name but with a
different type, since `Q<T>` filters on both — throws `InvalidOperationException` naming
the element, the expected type and the root searched under, plus the hint that the UXML
`name` attribute is where to look. Use it for every element a view cannot function
without; keep `Q<T>` for genuinely optional ones.

## The codegen, end to end — a ConfirmPopup

### 1. Write the UXML

`Assets/UI/ConfirmPopup.uxml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<ui:UXML xmlns:ui="UnityEngine.UIElements" editor-extension-mode="False">
    <ui:VisualElement name="popup-root">
        <ui:Label name="popup-title" text="Delete save?" />
        <ui:Label name="popup-body" text="This cannot be undone." />
        <ui:VisualElement name="button-row">
            <ui:Button name="btn-ok" text="OK" />
            <ui:Button name="btn-cancel" text="Cancel" />
        </ui:VisualElement>
    </ui:VisualElement>
</ui:UXML>
```

### 2. Enroll it — once, via the menu

Select the asset, right-click → **Assets/Cuvara/Generate UXML Bindings**. This writes
`Assets/UI/Generated/ConfirmPopup.uxml.g.cs`:

```csharp
// <auto-generated/> — generated from ConfirmPopup.uxml by Cuvara.UIToolkit codegen. Do not edit.
namespace Game.UI
{
    using UnityEngine.UIElements;
    using Cuvara.UIToolkit.Utilities;

    public partial class ConfirmPopup
    {
        public VisualElement PopupRoot { get; private set; }
        public Label PopupTitle { get; private set; }
        public Label PopupBody { get; private set; }
        public VisualElement ButtonRow { get; private set; }
        public Button BtnOk { get; private set; }
        public Button BtnCancel { get; private set; }

        public void AssignQueries(VisualElement root) { /* one Require<T> per property */ }
    }
}
```

Commit the generated file. It is source, reviewed like source — that is what makes the CI
drift check possible.

### 3. Consume it — a partial class of your own

The generated class is `partial` and has **no base type**, so it composes with any view
shape. The other half is yours; call `AssignQueries` in the constructor:

```csharp
namespace Game.UI
{
    using Cuvara.UIToolkit.View;
    using UnityEngine.UIElements;

    public partial class ConfirmPopup : BaseUIToolkitView
    {
        public ConfirmPopup(VisualTreeAsset asset) : base(asset)
        {
            this.AssignQueries(this.Root);
            this.BtnOk.clicked += this.OnConfirmed;
        }
    }
}
```

Any base — `BaseUIToolkitView`, an item presenter's view, or nothing at all — works the
same way; the generated half only ever adds properties and `AssignQueries`.

### 4. Auto-regen on save — the opt-in gate

From enrollment on, every reimport of `ConfirmPopup.uxml` (i.e. every save from UI Builder
or a text editor) regenerates the bindings automatically, via an `AssetPostprocessor`.
Two rules keep this safe:

- **Opt-in gate.** A UXML is regenerated **only if** its `Generated/<Name>.uxml.g.cs`
  already exists. The generated file's existence is the entire enrollment state — no
  settings asset, no registry. A UXML nobody enrolled is never touched; deleting the
  generated file un-enrolls.
- **Loop guard.** Writing a `.g.cs` triggers an import of its own. The pipeline therefore
  byte-compares before writing and skips both the write and the `AssetDatabase.Refresh`
  when the fresh content is identical — the steady state is zero writes, so imports settle.

A UXML that cannot generate (duplicate names, colliding properties — see below) logs an
error and leaves the previous generated file in place.

### 5. Drift check in CI

`Tools~/UxmlCodegenCli/` is a plain `dotnet` console project (Unity never imports `~`
folders) that compiles the **same** pure-core sources the Editor uses
(`Editor/Codegen/Core/` — Unity-free by contract), scans the given roots for enrolled
UXML, regenerates each in memory and byte-compares against the committed file:

```bash
dotnet run --project Packages/com.cuvara.uitoolkit/Tools~/UxmlCodegenCli/UxmlCodegenCli.csproj \
  -- Packages/com.cuvara.uitoolkit Assets
```

Exit 0 when everything matches; exit 1 listing every drifted file. The repository workflow
`.github/workflows/uxml-codegen-drift.yml` runs it on PRs touching UXML, generated
bindings, or the codegen itself. Someone who edits a UXML outside the Editor (or resolves
a merge by hand) and forgets to regenerate is caught here, not at runtime.

## Rules and conventions

**Class name** — the UXML file name, PascalCased: `ConfirmPopup.uxml` and
`confirm-popup.uxml` both yield `ConfirmPopup`.

**Property names** — PascalCase from the `name` attribute; every non-alphanumeric
character separates (`popup-title` → `PopupTitle`, `slot-2` → `Slot2`, `a--b` → `AB`,
`-leading` → `Leading`, `2nd-row` → `_2ndRow`).

**Namespace** — resolved per UXML file, walking from its directory upward:

1. a `.uxml-namespace` file — its trimmed content is the namespace (the configurability
   escape hatch, per subtree);
2. else the nearest `*.asmdef`'s `rootNamespace` (its `name` if that is empty) — the same
   namespace Unity gives a new script there, so the generated partial lands beside your
   hand-written half;
3. else `UxmlBindings`.

**Type mapping** — `ui:Label` → `Label`, `ui:Button` → `Button`, `ui:TextField`,
`ui:Toggle`, `ui:Slider`, `ui:ScrollView`, `ui:ListView`, `ui:Foldout`,
`ui:DropdownField`, `ui:ProgressBar` and the rest of the standard runtime controls map to
their `UnityEngine.UIElements` types; `ui:Instance` maps to `TemplateContainer`. An
unknown or custom tag becomes `VisualElement` with a comment naming the original tag.
`<ui:Template>` and `<Style>` are skipped — their `name` references an asset, not an
element in the cloned tree.

**Hard failures** (generation refuses, with a message listing the offenders):

- duplicate `name` values in one document;
- two names whose PascalCase forms collide (`popup-title` vs `popupTitle`);
- a name that PascalCases to the class name itself (element `confirm-popup` in
  `ConfirmPopup.uxml` — rename it, e.g. `popup-root`);
- a name yielding no identifier at all (`---`).

**Determinism** — properties and queries are emitted in document order, the header carries
no timestamp, output is UTF-8 without BOM with `\n` newlines. Regenerating from the same
input is byte-identical; that byte-identity is both the Editor's loop guard and CI's
drift check.

## Known limitation — batchmode sessions with compile errors do not regenerate

Renaming an element in an enrolled UXML regenerates its `.uxml.g.cs`, and any code still
using the old property name stops compiling. That compile error is the desired signal —
but it changes what a **batchmode** session can do afterwards. A `-batchmode -quit`
session that *starts* with compile errors logs `Scripts have compiler errors.` and exits
**before the asset import step**, so no `AssetPostprocessor` — this one included — ever
runs in it, and the process still exits 0. Verified on 6000.3.9f1 (2026-09-03): the
reverted UXML produced no import line in the log and the generated file was left stale.

Consequences:

- Reverting the UXML from that state does **not** regenerate the old bindings via
  batchmode. Recover with any of: `git checkout` the `.uxml.g.cs`, the
  **Assets → Cuvara → Generate UXML Bindings** menu item in an interactive Editor
  (an interactive session imports assets before compiling, so it self-heals), or
  `Tools~/UxmlCodegenCli` from the shell — the CLI compiles the generator core directly
  and does not care about the project's compile state.
- A CI job that opens Unity in batchmode expecting a regeneration must check the log for
  import lines and for `Scripts have compiler errors.` — the exit code alone proves
  nothing.
- Keep committed `.uxml.g.cs` files in sync with the code that consumes them (the drift
  workflow enforces the UXML side of this), so batchmode never starts dirty.

## Layout

| Piece | Where |
|---|---|
| `Require<T>` | `Runtime/Utilities/VisualElementQueryExtensions.cs` (`Cuvara.UIToolkit`) |
| Pure core (no Unity) | `Editor/Codegen/Core/` (`Cuvara.UIToolkit.Editor`, namespace `Cuvara.UIToolkit.Codegen`) |
| Menu + postprocessor | `Editor/Codegen/` |
| Drift CLI | `Tools~/UxmlCodegenCli/` — compiles `Editor/Codegen/Core/` with plain `dotnet` |
| Generator tests (string fixtures, also run under plain `dotnet`) | `Tests/Editor/UxmlBindingGeneratorTests.cs` |
| `Require` + generated-class tests | `Tests/Runtime/RequireQueryTests.cs`, `Tests/Runtime/GeneratedConfirmPopupTests.cs` |
| Enrolled examples, checked by CI | `Tests/Runtime/ConfirmPopup.uxml` + `Tests/Runtime/Generated/ConfirmPopup.uxml.g.cs`; `Samples~/EcsHud/VitalsView.uxml` + its `Generated/VitalsView.uxml.g.cs` (the partial-view half of the hybrid data-binding sample — see `HYBRID-DATA-BINDING.md`) |

The core stays Unity-free so the CLI can compile it — a `UnityEngine` using anywhere under
`Editor/Codegen/Core/` breaks the drift workflow's build, which is the enforcement.
